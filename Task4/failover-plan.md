# План отказоустойчивости и переключения

Документ отвечает на вопрос дежурного инженера: что происходит при каждом типе отказа, кто принимает решение о переключении, какие шаги выполняются, сколько это занимает и что теряется. Целевые значения — из `Task3/nfr-registry.md` (NFR-REL-01, NFR-REL-02) и `Task3/slo/`.

## Кто принимает решение

| Тип события | Решение принимает | Уведомляются |
| --- | --- | --- |
| Отказ зоны доступности | Автоматика провайдера; дежурный подтверждает | CTO |
| Потеря региона | CTO совместно с архитектором | Инвестор, CEO, CFO |
| Отказ локальной площадки с персональными данными | Дежурный переключает на вторую площадку; при отказе обеих — CTO объявляет региональную деградацию | Инвестор, CEO, внешний юрист |
| Приостановка обработки по требованию регулятора | CEO по согласованию с юристом | Инвестор, CTO |
| Возврат в нормальный режим | Дежурный по чек-листу; при потере региона — CTO | те же, кого уведомляли |

Право объявить деградацию есть у дежурного без согласования: остановка приёма заказов в одной стране дешевле, чем нарушение локализации или потеря денег.

## Сценарий 1. Отказ зоны доступности в af-south-1

**Что происходит:** недоступен основной экземпляр PostgreSQL или группа узлов Kubernetes в одной зоне.

| | |
| --- | --- |
| Обнаружение | Алерт мониторинга управляемой БД и рост ошибок соединения, до 2 мин |
| Решение | Автоматическое переключение на резервный экземпляр в другой зоне |
| Потеря данных | RPO ≤ 5 мин (синхронная репликация, последние незакоммиченные транзакции) |
| Время восстановления | RTO ≤ 30 мин |
| Поведение для покупателя | Витрина работает из кеша и CDN (до 15 мин устаревания); приём заказов приостановлен на время переключения; оформленные заказы не теряются |

**Шаги:** подтвердить автоматическое переключение → убедиться, что приложение переподключилось к новому основному экземпляру → проверить глубину очереди воркера и разобрать накопившееся → дозапросить у платёжных провайдеров статусы операций, начатых в момент отказа → сверить расчёты за период отказа → постмортем в течение двух рабочих дней.

## Сценарий 2. Потеря региона af-south-1

**Что происходит:** регион недоступен целиком (авария провайдера или отзыв доступа).

| | |
| --- | --- |
| Обнаружение | Недоступность всех точек входа, до 5 мин |
| Решение | CTO и архитектор, после подтверждения, что это не сетевая проблема на нашей стороне |
| Потеря данных | RPO ≤ 15 мин (последняя резервная копия и журнал) |
| Время восстановления | RTO ≤ 4 ч |
| Поведение для покупателя | Витрина отдаётся CDN в режиме «только просмотр»; приём заказов остановлен; на страницах и в SMS — сообщение о временной приостановке |

**Шаги:** объявить инцидент и уведомить инвестора и CEO → развернуть платформу из образов и конфигурации в запасном регионе (конфигурация хранится в репозитории, GitOps) → восстановить операционную базу из резервной копии → перенаправить трафик сменой записей DNS → восстановить подключение к локальным сервисам идентификаторов, которые аварией не затронуты → проверить обработку колбэков и выполнить сверку расчётов → возобновить приём заказов.

**Важное ограничение.** В запасной регион переносятся только обезличенные операционные данные. Персональные данные нигерийцев и кенийцев остаются в своих странах и в восстановлении не участвуют — это ограничение правовое, а не техническое, и шифрование его не снимает. Выбор запасного региона фиксируется до запуска и указывается в реестре трансграничных передач.

## Сценарий 3. Отказ локальной площадки с персональными данными

**Что происходит:** недоступна площадка NG-1 в Лагосе (или KE-1 в Найроби) — единственное место, где законно хранятся идентификаторы субъектов страны.

| | |
| --- | --- |
| Обнаружение | Алерт доступности сервиса идентификаторов, до 2 мин |
| Решение | Дежурный: переключение на вторую площадку того же провайдера в стране |
| Потеря данных | RPO ≤ 15 мин (репликация внутри страны) |
| Время восстановления | RTO ≤ 2 ч |
| Поведение для покупателя | Каталог и просмотр работают; оформление заказа в затронутой стране приостановлено; вторая страна работает в обычном режиме |

**Шаги:** переключить сервис идентификаторов на вторую площадку → проверить целостность данных контрольной выборкой → возобновить обработку очереди уведомлений и передачи заказов в доставку → уведомить юриста, если недоступность превысила 4 часа (возможны обязательства по уведомлению регулятора).

**Если недоступны обе площадки в стране.** Переезд за границу запрещён, поэтому объявляется региональная деградация: приём заказов в стране останавливается, уже оформленные заказы обрабатываются на стороне логистического партнёра, покупателям уходит SMS о задержке (номера берутся из очереди, которая находится в той же стране). Вторая страна и витрина продолжают работать. Оценка восстановления — до 8 часов; это худший сценарий в плане, и он принят сознательно: альтернатива означала бы нарушение требования локализации.

## Сценарий 4. Недоступность партнёрского сервиса

**Что происходит:** недоступен M-Pesa, Flutterwave, Sendbox, Sendy или SMS-шлюз.

| | |
| --- | --- |
| Обнаружение | Доля ошибок по провайдеру выше 10% за 10 мин |
| Решение | Автоматика: размыкание предохранителя и переключение на резервного провайдера, где он есть |
| Потеря данных | Нет: заказ и задача сохраняются в одной транзакции |
| Время восстановления | Определяется партнёром; повторы выполняются до 24 ч |
| Поведение для покупателя | Заказ принимается, статус «ожидает оплаты» или «доставка назначается»; уведомление при смене статуса |

Платежи в Нигерии переключаются с Flutterwave на Paystack; в Кении альтернативы M-Pesa нет, поэтому там работает только очередь с повторами. Уведомления переключаются между SMS и WhatsApp.

## Сценарий 5. Требование регулятора или отзыв согласия площадки

**Что происходит:** регулятор требует удалить контент (KICA), приостановить обработку или подтвердить локализацию.

| | |
| --- | --- |
| Обнаружение | Входящее обращение, фиксируется в журнале |
| Решение | CEO совместно с юристом |
| Время реакции | Блокировка контента ≤ 24 ч (NFR-CMP-03); ответ регулятору — в срок из обращения |
| Потеря данных | Нет |

**Шаги:** зафиксировать обращение → скрыть карточку или заблокировать продавца → подготовить выгрузку из реестра трансграничных передач и карты данных → ответить регулятору за подписью юриста → внести изменение в `data-residency-map.md`, если требование постоянное.

## Регулярные проверки

| Что проверяем | Как | Периодичность |
| --- | --- | --- |
| Переключение между зонами доступности | Учебное переключение на резервный экземпляр БД | Ежемесячно |
| Восстановление из резервной копии | Полное восстановление на тестовом стенде с замером времени | Ежемесячно |
| Переключение локальной площадки | Учение с переводом сервиса идентификаторов на вторую площадку | Раз в квартал |
| Деградация при отказе партнёра | Хаос-тест с отключением sandbox-эндпоинта | Перед каждым крупным релизом |
| Актуальность контактов и порядка эскалации | Проверка списка дежурных и телефонов | Ежемесячно |

Учение считается неуспешным, если фактическое время превысило целевое: в этом случае цель пересматривается или устраняется причина, но значения в реестре НФТ не подгоняются задним числом.

## Assumptions

- Запасной регион для сценария 2 не зафиксирован: выбор зависит от того, какие юрисдикции юрист признает допустимыми для обезличенных данных (вопрос Q4). До получения ответа восстановление планируется в пределах того же провайдера.
- Вторая площадка в Нигерии и Кении предполагается у того же локального провайдера; её наличие входит в критерии проверки провайдера (`cloud-regions-comparison.md`).
- Дежурство в пилоте — в рабочие часы с эскалацией, поэтому ночное время восстановления может превысить целевое; круглосуточное дежурство отложено (ADR-002).
- Значения RTO и RPO для локальных площадок (2 ч и 15 мин) приняты оценочно и подлежат подтверждению договором с провайдером.
