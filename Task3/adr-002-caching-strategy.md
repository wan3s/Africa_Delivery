# ADR-002: Стратегия кеширования и целевой уровень доступности

| | |
| --- | --- |
| **Статус** | Предложено |
| **Дата** | 20.08.2026 |
| **Владелец решения** | Инвестор — по целевому уровню доступности (он задал цену минуты); CFO — по расходам на резервирование |

| **Противоречие-источник** | C-02 (масштаб и доступность против бюджета), арт. 1 и 7 против арт. 6 |

## Контекст

Инвестор требует, чтобы система «не падала», и оценивает минуту простоя в \$12 000 (арт. 1, 7). CFO ограничивает инфраструктуру и SaaS суммой \$5 000/мес (арт. 6). Требование нужно перевести в уровень, который можно купить за эти деньги и проверить.

**Сколько стоит каждая девятка.** Ожидаемые потери считаются от выручки Года 1 (GMV \$7,5 млн), а не по ставке \$12 000/мин: проверка этой ставки — в `Task2/options-comparison.md`, она соответствует пиковой минуте распродажи примерно третьего года.

| Уровень | Простой в год | Ожидаемые потери | Что нужно добавить | Дополнительно в год |
| --- | --- | --- | --- | --- |
| 99,0% | 5 256 мин | \$112 тыс. | одна инстанция, резерва нет | базовая стоимость |
| 99,5% | 2 628 мин | \$56 тыс. | две и более реплик, автоперезапуск, резервные копии | +\$1,8 тыс. |
| **99,9%** | **526 мин** | **\$11,2 тыс.** | **БД в двух зонах, пробы, канареечный выпуск, CDN и кеш, дежурство в рабочие часы** | **+\$5,4 тыс.** |
| 99,95% | 263 мин | \$5,6 тыс. | прогретый резерв, дежурство 24/7 (0,5 FTE) | +\$46 тыс. |
| 99,99% | 53 мин | \$1,1 тыс. | второй регион active-active, 3–4 SRE | +\$270 тыс. |

Переход с 99,5% на 99,9% стоит \$3,6 тыс. и экономит \$45 тыс. — делаем. Переход с 99,9% на 99,95% стоит \$40 тыс. и экономит \$5,6 тыс. — в семь раз дороже выгоды. Четвёртая девятка окупается при GMV около **\$200 млн в год**, то есть примерно на третий-четвёртый год, — тогда же, когда минута простоя действительно начнёт стоить \$12 000.

**Важная оговорка.** Таблица описывает стоимость уровня для пути записи — оформление заказа и оплата. Для чтения каталога дополнительная девятка стоит на порядок дешевле: CDN и кеш продолжают отдавать контент, когда origin недоступен. Именно поэтому каталогу назначен уровень 99,95% в пределах той же инфраструктуры, а приёму заказа — 99,9%. Разные SLO по сервисам (`slo/`) — следствие того, что девятки для чтения и для записи стоят по-разному.

Дополнительно кеш решает две задачи, не связанные с отказами: пик дня запуска (1000 запросов в секунду при лимите 200 на origin, NFR-SCL-01) и экономию мобильного трафика на 3G (NFR-PRF-01, NFR-PRF-04).

## Рассмотренные варианты

| Вариант | Оценка |
| --- | --- |
| Без кеша, масштабировать origin под пик | Пик требует впятеро больше серверов (≈ +\$1,2 тыс./мес), не решает задержку на 3G и не даёт деградации при отказе БД. Отклонён |
| Только CDN на изображениях | Закрывает трафик, но не снимает нагрузку с API каталога и не спасает витрину при недоступности origin. Недостаточно |
| Redis как универсальный кеш всего, без политики | Быстро на старте, но без TTL и правил инвалидации приводит к показу устаревших цен и остатков, а отказ Redis становится отказом системы. Отклонён |
| **Многоуровневый кеш: клиент → CDN → приложение (Redis) → БД** | Каждый уровень закрывает свою задачу; политика TTL и инвалидации задаётся по типу данных. **Выбран** |

## Решение

Принимается целевой уровень доступности **99,9% для пути записи и 99,95% для чтения каталога** с управляемой деградацией, а не 99,99%. Пересмотр — при GMV выше \$200 млн в год либо через 6 месяцев после запуска по фактическим данным.

Кеширование — многоуровневое, с явной политикой по каждому типу данных:

| Данные | Где кешируется | TTL | Инвалидация | Поведение при отказе кеша |
| --- | --- | --- | --- | --- |
| Изображения товаров | CDN | 30 дней | Версия в имени файла: новая картинка — новый URL, старый не инвалидируется | Отдача из объектного хранилища, дороже по трафику |
| Списки и категории каталога | CDN + Redis (cache-aside) | 5 мин | По событию изменения товара через outbox: удаление ключей категории | Запрос в БД с ограничением параллелизма |
| Карточка товара | CDN + Redis | 15 мин | По событию изменения карточки (точечное удаление ключа) | То же |
| Результаты поиска | Redis | 2 мин | По TTL; принудительно не инвалидируется | Прямой запрос в БД |
| Цена и остаток | Redis, только для отображения | 30 с | По событию изменения; при оформлении заказа не используется | Прямой запрос в БД |
| Сессии и токены | Redis | равен сроку жизни токена | При выходе пользователя | Повторная аутентификация |
| Ключи идемпотентности платежей | Redis + БД (источник истины — БД) | 24 ч | По завершении операции | Проверка по БД, медленнее, но корректно |
| Каталог на устройстве покупателя | Приложение / PWA | 24 ч | Условный запрос по ETag при запуске | Загрузка из сети |

**Что не кешируется никогда:** цена и остаток в момент оформления заказа (проверяются в БД в той же транзакции), платёжные статусы, персональные данные, балансы выплат продавцам, данные бэк-офиса.

**Механика.** Инвалидация только событийная: изменение товара пишется в таблицу outbox в одной транзакции с самим изменением, воркер удаляет соответствующие ключи. Ручная очистка кеша в проде запрещена (CN.ADL.04). Против лавины запросов — однократный пересчёт ключа (single-flight), разброс TTL ±20% и отдача устаревших данных на время пересчёта. Перед распродажей кеш прогревается заранее.

**Redis — кеш, а не хранилище.** Потеря Redis допустима: любой ключ восстанавливается из БД. Поэтому Redis не резервируется отдельно, а при его недоступности приложение обращается в БД с ограничением параллелизма (Bulkhead), чтобы не уронить базу.

## Границы решения (что мы НЕ делаем сейчас)

| Отложено | Триггер возврата |
| --- | --- |
| Второй регион и уровень 99,99% | GMV выше \$200 млн в год либо решение инвестора оплатить +\$270 тыс. в год |
| Дежурство 24/7 | рост доли ночных заказов выше 20% либо выход в третий часовой пояс |
| Кеш в памяти процесса (L1) поверх Redis | доля попаданий в Redis ниже 90% или P99 каталога выше 300 мс |
| Предварительный расчёт персональных лент и рекомендаций | появление функции рекомендаций (вне MVP) |

## Последствия

**Положительные.** До 80–90% чтения каталога обслуживается вне origin, что делает выполнимым требование 1000 запросов в секунду при лимите 200 на origin и укладывает инфраструктуру в 51% бюджета CFO. Витрина переживает недоступность БД до 15 минут (NFR-AVL-06) — это и есть та «управляемая деградация», которой заменено обещание «никогда не падать». Трафик на 3G сокращается за счёт долгого кеша изображений.

**Отрицательные.** Покупатель может видеть цену и остаток с задержкой до 30 секунд, а состав категории — до 5 минут; при оформлении заказа возможна ситуация «товар закончился, пока вы смотрели», её обрабатывает сценарий оформления. Событийная инвалидация добавляет связность: забытая публикация события в outbox приводит к устаревшим данным, которые не самоисправятся до истечения TTL. Появляется третье состояние системы («работает из кеша»), которое нужно отдельно отображать в мониторинге, иначе деградация останется незамеченной.

**Риски и меры.** Лавина после инвалидации — single-flight и разброс TTL (FM-08). Расхождение кеша и БД — TTL как страховка: любые данные самовосстанавливаются не дольше чем за 15 минут. Незаметная деградация — отдельная метрика доли попаданий и возраста ключей, вынесенная в дашборд (см. `observability.md`).

## Обратимость и точка пересмотра

Решение дешёвое в отмене: уровни кеша отключаются конфигурацией, контракты API не меняются. Снижение TTL до нуля переводит систему в режим прямых запросов к БД — это допустимо при нагрузке пилота и служит аварийным рычагом при подозрении на некорректные данные. Пересмотр уровня доступности — через 6 месяцев после запуска либо при достижении GMV \$200 млн в год.
