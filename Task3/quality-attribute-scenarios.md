# Quality Attribute Scenarios

## QAS-01. Отказ платёжного провайдера в пик

| Поле | Значение |
| --- | --- |
| Источник стимула | Внешний платёжный провайдер M-Pesa |
| Стимул | API перестаёт отвечать (таймауты на 100% запросов) |
| Артефакт | Модуль `payments`, фоновый воркер, очередь платёжных намерений |
| Условия среды | Пик дня запуска: 50 заказов в минуту, идёт флеш-распродажа |
| Реакция | Размыкается предохранитель (circuit breaker), заказ сохраняется вместе с задачей на оплату в одной транзакции, покупатель видит статус «ожидает оплаты», воркер повторяет попытку с нарастающей паузой; при недоступности дольше 5 минут новые платежи направляются на резервного провайдера |
| Мера реакции | 100% заказов принято; ни один заказ не потерян; P99 отклика «создать заказ» не превышает 800 мс; оплата повторно инициируется в течение 15 минут |
| Источник требования | NFR-AVL-04, NFR-PRF-03, арт. 1 |

## QAS-02. Отказ логистического партнёра

| Поле | Значение |
| --- | --- |
| Источник стимула | Партнёрский API доставки Sendbox (Нигерия) |
| Стимул | API возвращает ошибки на все запросы создания отправления в течение часа |
| Артефакт | Модуль `logistics`, фоновый воркер, очередь задач на передачу заказа |
| Условия среды | Обычный рабочий день, средний поток заказов |
| Реакция | Заказ создаётся и оплачивается как обычно; задача на передачу в доставку остаётся в очереди и повторяется с нарастающей паузой; покупатель получает уведомление «заказ оформлен, доставка назначается»; при недоступности дольше 2 часов оператору поддержки создаётся задача на ручную передачу |
| Мера реакции | 0 потерянных заказов; повторы продолжаются до 24 часов; после восстановления партнёра очередь разбирается за ≤ 15 минут; доступность приёма заказа не опускается ниже 99,9% |
| Источник требования | NFR-AVL-05, NFR-REL-04, R2 |

## QAS-03. Задержка витрины на мобильной сети

| Поле | Значение |
| --- | --- |
| Источник стимула | Покупатель со смартфона до 150 USD |
| Стимул | Открывает витрину по диплинку из рекламы и пролистывает первый экран каталога |
| Артефакт | Мобильное приложение, CDN, модуль `products`, кеш каталога |
| Условия среды | Сеть 3G с потерями пакетов, час пик дня запуска, кеш CDN прогрет |
| Реакция | Первый экран собирается из кеша CDN, изображения отдаются в WebP с адаптивным размером, дозагрузка остального каталога идёт в фоне |
| Мера реакции | Время до первого товара: P75 ≤ 2,0 с, P95 ≤ 4,0 с (метрика реальных пользователей); P99 ответа origin ≤ 300 мс; вес первого экрана ≤ 500 КБ; доля запросов, обслуженных CDN, ≥ 80% |
| Источник требования | NFR-PRF-01, NFR-PRF-02, NFR-PRF-04, арт. 2 |

## QAS-04. Пик дня запуска

| Поле | Значение |
| --- | --- |
| Источник стимула | Маркетинг: push-уведомление по всей базе, SMS и старт флеш-распродажи с таймером |
| Стимул | За 5 минут после рассылки нагрузка вырастает до 1000 запросов в секунду к каталогу и 50 заказов в минуту |
| Артефакт | CDN, ingress, реплики приложения, пул соединений к PostgreSQL, воркер уведомлений |
| Условия среды | 15 октября, первый час после старта кампании; рассылка и покупательский трафик идут одновременно |
| Реакция | CDN поглощает основную часть чтения; число реплик приложения увеличивается автоматически; отправка уведомлений идёт в отдельном процессе и ограничена по скорости, чтобы не выедать пул соединений (bulkhead); при исчерпании пула включается очередь ожидания вместо отказа |
| Мера реакции | На origin приходит ≤ 200 запросов в секунду; доля ошибок < 0,05%; P99 каталога деградирует не более чем на 20% от нормы; удвоение мощности занимает ≤ 10 минут без простоя; ни одно уведомление не потеряно |
| Источник требования | NFR-SCL-01, NFR-SCL-02, NFR-AVL-03, R4 |

## QAS-05. Отказ зоны доступности с базой данных

| Поле | Значение |
| --- | --- |
| Источник стимула | Облачный провайдер: авария в зоне доступности |
| Стимул | Основной экземпляр PostgreSQL становится недоступен, приложение теряет соединения |
| Артефакт | Управляемый PostgreSQL, реплика в соседней зоне, модули `orders` и `payments`, кеш каталога |
| Условия среды | Обычный день, идёт приём заказов; часть платежей находится в состоянии «ожидает подтверждения» |
| Реакция | Выполняется переключение на реплику в другой зоне; витрина в это время отдаёт каталог из кеша и CDN; приём заказов приостанавливается и возобновляется после переключения; незавершённые платежи дозапрашиваются у провайдера по идентификатору операции |
| Мера реакции | RTO ≤ 30 минут, RPO ≤ 5 минут; витрина доступна в режиме чтения в течение всего переключения (до 15 минут устаревания); 0 подтверждённых платежей потеряно; расхождений при последующей сверке с провайдером — 0 |
| Источник требования | NFR-REL-01, NFR-AVL-06, арт. 5 (RPO = 0 отклонён в ADR-001) |

## QAS-06. Повторный колбэк платёжного провайдера

| Поле | Значение |
| --- | --- |
| Источник стимула | M-Pesa: механизм повторной доставки колбэков |
| Стимул | Один и тот же колбэк о подтверждении оплаты приходит трижды (первый ответ не был получен провайдером из-за сетевой ошибки) |
| Артефакт | Приёмник колбэков, модуль `payments`, таблица идемпотентности, модуль `orders` |
| Условия среды | Обычная работа, возможен параллельный приход дублей в один момент |
| Реакция | Каждый колбэк обрабатывается по ключу идемпотентности провайдера: первый переводит заказ в оплаченный статус, повторные распознаются как дубли и возвращают тот же ответ без повторного изменения данных; конкурентные дубли отсекаются блокировкой записи |
| Мера реакции | 0 двойных списаний и 0 повторных заказов; на все дубли возвращается успешный ответ (провайдер прекращает повторы); расхождение при ежедневной сверке — 0; обработка дубля занимает ≤ 100 мс |
| Источник требования | NFR-REL-03, C-08, арт. 3 |

## Assumptions

- Структура из шести полей взята из модели ATAM (источник стимула, стимул, артефакт, условия среды, реакция, мера реакции): «приложение В» в выданных материалах отсутствует.
- Числовые меры реакции совпадают с целевыми значениями реестра НФТ и SLO-контрактов; при изменении реестра сценарии обновляются вместе с ним.
